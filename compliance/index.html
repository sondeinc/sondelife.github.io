    Compliance

    Compliance has a code-level gap.

    Infrastructure tools can tell you how cloud resources are configured. Sonde shows what the product interface and the source code actually do.

    Compliance reporting across global standards

    Sonde compliance reports are built from deterministic probes over the same semantic graph that powers the rest of the platform. The current reporting paths cover accessibility evidence, security and privacy evidence, software supply-chain evidence, and regional or industry standards as supported racks are enabled. The result is not a separate checklist layer; it is standards evidence grounded in what the product and code actually do.

    Accessibility evidence for the interface and the code

    Sonde's accessibility analysis spans the rendered device interface and the implementation behind it: browser UI, mobile app, desktop app, HTML, JSX/TSX, Swift, and Objective-C today, with the roadmap covering SwiftUI/UIKit, Android XML/Java, Jetpack Compose/Kotlin Multiplatform, XAML/.NET MAUI/Xamarin.Forms, React Native, Dart/Flutter, Delphi VCL/FireMonkey, JSP/JSTL, JSF/Facelets/PrimeFaces, Thymeleaf/Spring MVC views, Vaadin, JavaFX, and Swing. Findings can point to what a user experiences and where a developer can fix it.

    The patent-pending three-face architecture

    Most accessibility tools see only what your browser shows them. Sonde sees the source code that made it. The same scan that flags a missing label on a button traces the violation back to the exact file, line, and component that built it, and emits a deterministic fix recipe. This is the patent-pending architecture behind every Sonde compliance report.

    Three correlated lenses turn accessibility from a launch-blocker audit into a deterministic, in-development checkpoint. The same architecture extends to native iOS and Android applications, Apple Human Interface Guidelines compliance, Material Design compliance, brand consistency between platforms, and cross-device parity.

    Face 1 — Source-aware static analysis

    Before a single page renders, Sonde reads the source code that produces the user interface. JSX, HTML, SwiftUI, UIKit, Jetpack Compose, Android XML, React Native, Flutter, .NET MAUI, and Xamarin all map into a unified element model that captures labels, traits, semantics, hidden state, identifiers, gesture handlers, frame and layout dimensions, dynamic-type signals, and platform-specific style references. Static probes flag missing accessibility properties, broken landmark structure, mis-applied semantics, mechanically provable Material Design and Apple Human Interface Guidelines violations, and platform-specific anti-patterns at the source — before any user ever sees the bug. If your preferred framework is missing, let us know and we’ll add it!

    Face 2 — Live runtime analysis

    Source files cannot prove how a real browser renders the page or how an actual device exposes the screen to assistive technology. Sonde runs the live UI in a real Chromium instance — the same engine the majority of users open the web through — and inspects the rendered DOM with the full battery of WCAG, ARIA, behavioral, focus-order, contrast, and announcement probes. Mobile apps run inside their actual iOS Simulator or Android Emulator, with native VoiceOver and TalkBack accessibility trees captured directly from the device through the platform's own accessibility APIs. The same rack architecture that runs web probes runs mobile probes; the same evidence model holds the findings.

    Face 3 — Source correlation

    The third face is what makes the system unique. Every runtime finding traces back to the exact source line that produced it. For browsers, Sonde follows source maps, React fibers, CSS selectors, and component identifiers. For mobile, view-hierarchy identifiers, test IDs, layout XML references, storyboard outlets, and build artifacts (dSYM symbols and ProGuard mapping.txt) anchor each finding to its origin in the Swift, Kotlin, Dart, Java, or TypeScript codebase. Confidence scoring per strategy makes the trace auditable: a finding with a high-confidence accessibility identifier match is treated differently from a string-literal heuristic. No other accessibility tool ties UI-level findings back to the source code that produced them at this fidelity.

    Deterministic fix plans, not suggestions

    Because the violation is anchored to a known source location AND a known rule, Sonde emits a deterministic fix recipe — not a model-generated guess. Mechanical fixes ship as exact patches: add a missing label attribute, raise a touch target above the platform minimum, replace a literal color with a design token, swap a hidden-from-AT container for a non-semantic wrapper. Context-dependent fixes ship as review-required recipes the development team owns: rewriting a label for clarity, restructuring a navigation flow, choosing the right ARIA role for a custom component. The same source-anchored evidence drives the auto-fix engine that Sonde's integrated tooling applies on demand: apply the recipe, rerun the static extractor, rerun the live probe where applicable, and prove the finding clears without introducing new accessibility or design findings.

    Web, mobile, and cross-platform coverage

    The same three-face architecture extends to native iOS and Android applications. Sonde checks Apple Human Interface Guidelines compliance for SwiftUI and UIKit, Material Design compliance for Jetpack Compose and Android Views, and cross-platform parity for React Native, Flutter, Kotlin Multiplatform, and .NET MAUI / Xamarin builds — every framework folded into the same source-correlated model. Cross-platform parity probes catch findings that exist on one platform but not the other: an iOS-only missing label, an Android-only touch-target violation, a React Native or Kotlin Multiplatform abstraction that produces an unequal accessibility tree across platforms.

    Brand enforcement and cross-device comparison

    The same device-automation infrastructure that captures accessibility evidence captures brand evidence. Run the iOS and Android builds of the same product side by side and Sonde flags color drift between platforms (your iOS primary button is one shade and your Android button is another, against your design token), icon mismatches (SF Symbols on iOS, a custom SVG on Android), typography drift (effective visual size differs across platforms), and layout deviations beyond design-system tolerance. Cross-device comparisons (phone vs. tablet, light vs. dark themes, different paper sizes for printed exports) build on the same evidence model. The buyer who recognizes this is the design-system team that today does these audits manually — nobody else automates them.

    What is the Sonde Score?

    The Sonde Score is a universal 0–1000 compliance index that measures how accessible a website is. It works like a credit score for digital accessibility — higher is better, and the methodology is published openly. The 1000-point scale provides fine-grained differentiation between sites and avoids the misleading "percent correct" interpretation.

    The score is normalized per page scanned, so sites of any size can be compared fairly. A 50-page site with 100 findings and a 5-page site with 10 findings of the same severity distribution receive the same score. A score of 500 means the site’s per-page weighted penalty exactly equals the sensitivity parameter.

    The Formula

    Score = round(1000 × S / (S + P/N))

    where S = sensitivity (750), P = Σ(weight × count), N = pages scanned

    Each accessibility finding carries a severity weight. The sum of all weighted findings is divided by the number of pages scanned to normalize for site size. A harmonic curve maps the result to a 0–1000 index, ensuring every site gets a meaningful score with no zeros.

    Element Compliance Rate (ECR)

    The Element Compliance Rate measures what fraction of a website’s UI elements are free of accessibility findings. While the Sonde Score measures the severity-weighted depth of issues, the ECR measures the breadth of compliance across the entire DOM.

    ECR = ((Total Elements − Elements with Findings) / Total Elements) × 100

    Total Elements is the count of all DOM nodes on each page. Elements with Findings counts unique CSS selectors that have at least one accessibility violation. A page with 500 elements and 12 elements with findings has an ECR of 97.6%. The two metrics together give a complete picture: the Sonde Score tells you how serious the issues are; the ECR tells you how widespread they are.

    Section 508 and WCAG

    The Section 508 refresh (2017) adopted WCAG 2.0 Level AA as the technical standard for federal agencies. WCAG 2.1 AA is a strict superset of 2.0 AA. Sonde scans against WCAG 2.1 AA and maps findings to both WCAG success criteria and Section 508 provision numbers, so reports show dual references.

    How Sonde Scans

    Every finding in a Daylight report is produced by deterministic algorithms — no AI, no large language models, no tokens consumed. This is a deliberate design choice with real consequences.

    • 100% consistent. Run the same scan twice, get identical results. There is no randomness, no temperature parameter, no model drift.
    • Repeatable and verifiable. Fix a violation in your code, rescan, and confirm the finding is gone. Every fix is provable because the analysis is provable.
    • Full provenance. Every finding traces back to the specific rule or probe that detected it, the DOM element that triggered it, and where possible the source code location responsible.
    • No hallucinations. Deterministic rules either match or they don’t. Sonde will never invent a violation that doesn’t exist or miss one because a model was having a bad day.

    This matters for procurement, for legal compliance, and for trust. When a VPAT says “Does Not Support,” that judgment is backed by a reproducible algorithm — not a probability estimate.

    VPAT (Voluntary Product Accessibility Template)

    Each scanned site includes a downloadable VPAT — the industry-standard format for documenting product accessibility conformance. Published by the Information Technology Industry Council (ITI), the VPAT is widely used in government and enterprise procurement to evaluate whether a product meets accessibility requirements.

    Our VPAT reports cover all 50 WCAG 2.1 Level A and Level AA success criteria. Each criterion is rated as Supports (no violations detected), Partially Supports (violations on some pages), Does Not Support (violations across all pages), or Not Evaluated (requires human judgment beyond automated testing). The VPAT also includes the Section 508 crosswalk for each criterion.

    Learn more about the VPAT format

    OSCAL (Open Security Controls Assessment Language)

    Each scanned site includes a downloadable assessment results file in OSCAL format — a standardized, machine-readable data format developed by NIST for expressing security and compliance assessment information.

    OSCAL enables automated processing of compliance data across tools and organizations. Government agencies and their contractors increasingly use OSCAL for FedRAMP authorization packages, continuous monitoring, and supply chain risk management. Our OSCAL export follows the Assessment Results model, making scan findings directly consumable by GRC (Governance, Risk, and Compliance) platforms and procurement workflows.

    Learn more about OSCAL at NIST

    Why some scans come back "incomplete"

    Every leaderboard row carries a status flag. Most read "complete" — the crawler reached the site, rendered pages in a real Chromium instance, and ran the full probe suite against them. A small number read "incomplete" and show an — instead of a Sonde Score. Those are the sites where the scan reached the origin but the origin refused to produce a usable response.

    Sonde is a polite crawler by design. We publish a Sonde User-Agent so operators can allow-list us; we honor robots.txt `Disallow` directives and any published `Crawl-delay`; and between requests we sleep a jittered interval drawn from a triangular distribution so our traffic doesn’t look like an exact-periodicity stress test. When a host’s edge (Cloudflare, Akamai, DataDome, Imperva, F5, PerimeterX) serves a challenge interstitial, Sonde cools down and retries once with a fresh browser tab. If the second attempt also hits the challenge, we mark the scan incomplete and move on rather than escalate.

    Concretely, a scan is flagged incomplete when one of these happens:

    • Zero pages were analyzed — typically because every request was blocked before any page was rendered.
    • The crawl was cut short mid-run by a transport error (disconnect, timeout, browser crash) before it could reach representative pages.
    • Site-scope mode returned only a single page even though the sitemap or home page promised many more — a common signature of a login wall or a challenge page hiding the real content from anonymous traffic.

    Incomplete rows are NOT a score of zero, and they are not a judgment about the operator’s site. They are a measurement of our ability to read the site from outside without authentication — and a small but real subset of public sites have bot-detection rules strict enough that no polite headless crawler can produce a clean scan. For those cases we publish the status honestly and invite the operator to reach out so we can complete the review through another channel.

    Allowlisting Sonde

    Site operators who want a complete Sonde Daylight scan can allow our crawler deliberately. Sonde scanner traffic is transparent by design — we do not cloak fingerprints, rotate IPs, or attempt CAPTCHA bypass. The trade-off is that polite traffic is also blockable traffic; the sections below describe what we send, what we do not send, and how to recognize our requests.

    What Sonde sends

    • Read-only HTTP GET and HEAD against public URLs only. No state-changing methods.
    • Headless Chromium running real page renders, executing JavaScript and CSS the same way a human visitor’s browser would.
    • Honors `robots.txt` `Disallow` rules and any published `Crawl-delay`. Out-of-band fetches (sitemap, robots.txt) use the same User-Agent as the page renders.
    • A `Sonde/0.1` product token leads the User-Agent string, followed by the underlying Chromium UA and a human-readable suffix — e.g. `Mozilla/5.0 (…) Chrome/… Sonde/0.1 (+https://daylight.sonde.life; Accessibility Auditor)`.
    • Single-digit requests per second per site, jittered between requests with a triangular distribution so traffic does not look like an exact-periodicity stress test.

    What Sonde does NOT send

    • No aggressive concurrency. Per-site fan-out is bounded; the global crawler concurrency is not weaponised against any single host.
    • No proxy, residential-IP rotation, or hidden egress. Scanner traffic is attributable to whoever runs the scan.
    • No fingerprint cloaking, no spoofed `navigator` properties, no synthetic mouse/keyboard noise, no stealth-browser plugins.

    Opt-in for customer-specific scans

    By default these behaviours are off in unattended and public scans. Customer-specific scans can opt them in:

    • No POST, PUT, DELETE, or any state-changing request.
    • No authentication attempts. Sonde never submits credentials, cookies harvested from third parties, or session tokens.
    • No form submission. We read forms; we do not interact with them.

    How to allowlist

    Vendor-neutral guidance, in order of preference:

    1. Match the `Sonde/` token in the User-Agent string and allow GET and HEAD from that match. The token is stable across releases; the trailing version (`0.1` today) will tick forward but the leading `Sonde/` substring will not change.
    2. Contact-on-block: where your edge supports an "alert and allow" workflow, route Sonde matches to a human review queue rather than a hard block. We respond to operator queries at `daylight@sonde.life`.
    3. Combine the UA match with a conservative rate-limit threshold. Sonde scanner traffic is single-digit RPS per site — anything beyond that, even from a `Sonde/` UA, is not us.

    Frank caveat: the `Sonde/` User-Agent token alone cannot prevent impersonation. UA strings are trivially spoofable. Treat the UA recommendation as one signal among several — ideally combined with rate-limit thresholds and, once available, IP-based allowlisting against a published Sonde egress range. Operators concerned about impersonation should not rely on the UA recommendation as a sole gate.

    Egress honesty

    Sonde does not currently operate a stable public scanner egress. Many Daylight scans run from operator-controlled hosts — contributors, customers, or Sonde staff machines — and the source IP for a given scan is not predictable in advance. IP-based allowlisting is therefore not yet possible. When Sonde stands up a hosted scanner, traffic will originate from `*.sonde.life` and the published egress range will be added here. Until then, the User-Agent token plus rate-limit threshold are the strongest signals available.

    Vendor-specific guidance

    Cloudflare, Akamai Bot Manager, Imperva, F5, DataDome, and PerimeterX each expose their own rule editor. The general pattern is identical: a custom rule that matches the `Sonde/` UA token, allows GET and HEAD methods, and treats the source as a known good-bot tier. Worked rule snippets for each vendor will be published here as Sonde validates them against actual customer dashboards — until a snippet has been verified end-to-end (rule deployed, scan re-run, scan completes), this section ships vendor-neutral.

    Accessibility before launch, not after

    When a finding lives in the source repo with a known fix, it integrates into the pre-launch development loop the same way unit tests do. A pull request can fail because of an accessibility regression with the same fidelity as a type-check failure. Sonde's CI surface emits SARIF, OSCAL, VPAT, and PR-comment annotations; the IDE surface (Sonde Cockpit, MCP, and LSP integrations) can apply the deterministic fix recipe the moment the finding appears. That moves accessibility out of post-launch audit purgatory and into the deterministic checks every shipping team already runs.
