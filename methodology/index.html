    Methodology

    Provable analysis, not confident guesses.

    Sonde is deterministic by design. It parses software into evidence, runs probes that leave auditable mutations, and ties every claim back to source facts that can be inspected and rerun.

    How Sonde keeps analysis honest

    Evidence before opinion

    Sonde starts with parse trees, build graphs, package metadata, resource declarations, schema signals, and runtime evidence instead of model-generated summaries.

    Provenance on every claim

    Findings retain the path back to the code, manifest, dependency, resource, or probe result that produced them.

    Composable probes

    Probes can consume earlier probe output, so the analysis swarm builds stronger system-level conclusions from smaller deterministic observations.

    Rerunnable remediation

    Fix plans are only useful if the same analysis can run again and prove whether the risk, smell, or compliance gap actually changed.

    The Sonde analysis loop

    Discover

    Build resolvers, language profiles, resource detectors, and manifests describe what is actually present.

    Analyze

    Racks coordinate probes for architecture, quality, accessibility, compliance, agent safety, project intelligence, resources, and remediation.

    Query

    SondeQL and product surfaces ask questions over the same semantic mesh, from quick ad hoc checks to full workflows in the browser-based Cockpit.

    Prove

    Reports, lint output, MCP responses, and Cockpit views all point back to the same evidence so a result can be shared, reviewed, and rerun.

    How Sonde sees your code — the three-face architecture

    Most accessibility tools see only what your browser shows them. Sonde sees the source code that made it. The same scan that flags a missing label on a button traces the violation back to the exact file, line, and component that built it — and produces a deterministic fix recipe. The patent-pending architecture extends from the web to native iOS and Android, Apple Human Interface Guidelines compliance, Material Design compliance, brand consistency, and cross-device parity.

    Face 1 — Source-aware static analysis

    Before a single page renders, Sonde reads the source code that produces the UI. JSX, HTML, SwiftUI, UIKit, Jetpack Compose, Android XML, React Native, Flutter, .NET MAUI, and Xamarin all map into a unified element model. Static probes flag missing accessibility properties, mis-applied semantics, and platform-specific anti-patterns at the source — before any user ever sees the bug. If your preferred framework is missing, let us know and we’ll add it!

    Face 2 — Live runtime analysis

    Source files cannot prove how a real browser renders the page. Sonde runs the live UI in a real Chromium instance and inspects the rendered DOM with the full battery of WCAG, ARIA, and behavioral probes. Mobile apps run inside the actual iOS Simulator or Android Emulator, with native VoiceOver and TalkBack accessibility trees captured directly from the device.

    Face 3 — Source correlation

    Every runtime finding traces back to the exact source line that produced it. For browsers, Sonde follows source maps, React fibers, CSS selectors, and component identifiers. For mobile, view-hierarchy identifiers, test IDs, layout XML references, storyboard outlets, and build artifacts (dSYM symbols, ProGuard mapping.txt) anchor each finding to its origin in the Swift, Kotlin, Dart, Java, or TypeScript codebase.

    Deterministic fix plans, not suggestions

    Because the violation is anchored to a known source location AND a known rule, Sonde emits a deterministic fix recipe — not a model-generated guess. Mechanical fixes (add a missing label, raise a touch target above the platform minimum, replace a literal color with a design token) ship as exact patches. Context-dependent fixes ship as review-required recipes the development team owns.

    Web, mobile, and cross-platform coverage

    The same three-face architecture extends to native iOS and Android. Sonde checks Apple Human Interface Guidelines compliance for SwiftUI and UIKit, Material Design compliance for Jetpack Compose and Android Views, and cross-platform parity for React Native, Flutter, Kotlin Multiplatform, and .NET MAUI / Xamarin builds.

    Brand enforcement and cross-device comparison

    The same device-automation infrastructure that captures accessibility evidence captures brand evidence. Run iOS and Android side by side and Sonde flags color drift, icon mismatches, typography differences, and layout deviations beyond design-system tolerance. Cross-device comparisons (phone vs. tablet, light vs. dark themes, different paper sizes for printed exports) build on the same evidence model.

    Accessibility before launch, not after

    When a finding lives in the source repo with a known fix, it integrates into the pre-launch development loop the same way unit tests do. A pull request can fail because of an accessibility regression with the same fidelity as a type-check failure. That moves accessibility out of post-launch audit purgatory and into the deterministic checks every shipping team already runs.

    Patent pending. The multi-face source-correlated accessibility scanning architecture is the subject of filed Sonde patent applications. Methodology is described here at the conceptual level; specific algorithms, fixture formats, and fix-recipe schemas remain governed by the underlying applications.

    Sonde on Sonde

    Sonde is developed under its own standard racks and probes. Localization, theme tokens, anchor coverage, Cockpit accessibility, public/private package boundaries, and code review debt all run against the product itself so the Cockpit and the rest of the platform stay honest as they ship.
